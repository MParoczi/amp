# Phase 03 — leaner runs: Spec

## 1. Goal

Make an amp run faster and cheaper in tokens with the same quality gates. Every review, test gate
and verification stays; what changes is how agents are re-used, what they load, how hard the
mechanical roles think, what the orchestrator re-reads, how tasks are sized and sequenced, and how
often the full suite runs. Phase 03, type `framework`, branch `framework/03-leaner-runs`. Both
trees (Claude Code and Codex) change, from `src/`.

## 3. Architecture

No new files except this spec and its plan. All behavior is text in `src/` (rendered to `skills/`,
`agents/`, `codex/`) plus manifest/hook help strings.

### 3.1 Re-review by the resumed reviewer (D1)

- amp:build records each task reviewer's agent id (as it already does for the implementer). After
  a fix round, the orchestrator sends the filled `prompts/re-review.md` to that reviewer. The
  template's scope rules (verdict each finding; new breakage inside the fix diff only; out-of-scope
  observations never block) bind whoever receives it.
- When resuming, the `Load:` line of the template is omitted (the reviewer already holds its
  skills); a fresh checker gets it.
- Fallback: only when the resume fails (agent gone, resume error), dispatch a fresh `amp:checker`
  with the same template. Ledger `Re-review: checker (reviewer not resumable: <why>)`.
- Final review: the final fix wave's re-check resumes the final reviewer, same fallback.
- Document reviews (spec, plan, roadmap): the one confirmation re-review resumes the same reviewer
  with "Confirmation re-review: the document changed; verify each Critical/Important issue you
  raised is resolved and flag only new Critical/Important problems in the changes." Same fallback
  (a fresh reviewer with the document-review template).
- Codex: reviewers stay open until their task's fix loop (or the document's confirmation) ends,
  then close. The fallback checker keeps the name `checker_<N>_r<R>`.
- The reviewer agent definition gains one line: a re-review message replaces its full-review
  scope with the message's scope.

### 3.2 Pipelined task (D6)

Plan field (optional, default no): `**Independent:** yes` on task N+1 means it consumes nothing
task N produces and shares no file with task N. amp:build's preflight conflict scan confirms each
mark or overrides it with a ruling.

**Worktree path: inside the workspace**, `WT="$WS/wt-<N+1>"` (`$WS` is already a native path that
file tools open, and it stays inside the project, so Claude Code edits there need no extra
permission; Claude Code's own worktrees also live inside the project). `.amp/` is git-ignored, but
some tools don't read `.gitignore`. While a pipeline is open: reference and dead-code checks use
`git grep` (tracked files only), and the implementer and reviewer prompts name the worktree path; a
test or lint failure whose path is under `.amp/` is a pipeline artifact, re-run with `.amp` excluded,
not a finding. Claude Code's native `isolation: "worktree"` is not used: Codex has no equivalent, and
the orchestrator must control the base, the branch name and the rebase/merge.

Loop, when task N's implementer reports DONE (or DONE_WITH_CONCERNS once resolved) and task N+1
is Independent:
1. `bash "$S/task-brief" <plan> N+1 $WS`, then `git worktree add "$WT" -b amp-wt-<N+1>` (from the
   current HEAD = N's head). Ledger `Task N+1: pipelined (worktree <WT>)`. Run the project's
   documented install/setup in it if its tests need one; if that fails, or the tests need setup the
   project doesn't document, remove the worktree, ledger `Pipeline: off — <why>`, and run the rest
   of the plan sequentially.
2. Dispatch task N's reviewer and task N+1's implementer (`Work in: <WT>` on branch
   `amp-wt-<N+1>`) together. N's fix loop runs as usual in the main tree.
3. When N is complete **and** N+1's implementer has returned its contract (wait for it otherwise):
   if N gained fix commits, `git -C "$WT" rebase <phase branch>` (N+1's commits are unreviewed, so
   the rewrite is safe). A conflict → `git -C "$WT" rebase --abort`, then cleanup (below), ledger
   `Task N+1: pipeline dropped — <why>`, and run N+1 sequentially from scratch. A clean rebase →
   resume N+1's implementer to re-run its tests in the worktree.
4. `BASE=$(git rev-parse HEAD)`; ledger `Task N+1: merged (base <BASE>)`; then
   `git merge --ff-only amp-wt-<N+1>` and cleanup. Review N+1 as usual on `BASE..HEAD`.

**Cleanup** (every exit): `git worktree remove --force "$WT"` and `git branch -D amp-wt-<N+1>`
(`-D`: after a drop the branch is unmerged).

At most one task runs ahead. Never two implementers in the **same** tree. Codex follows the same
steps (two implementers open is within the default thread limit).

## 5. Interfaces

- Plan task field: `**Independent:** yes` (absent = no).
- Ledger lines: `Re-review: checker (reviewer not resumable: <why>)`,
  `Task N+1: pipelined (worktree <WT>)`, `Task N+1: merged (base <BASE>)`,
  `Task N+1: pipeline dropped — <why>`, `Pipeline: off — <why>`.
- Worktree path `$WS/wt-<N+1>` (native path), temp branch `amp-wt-<N+1>`.
- Codex spawn effort: `reasoning_effort: "medium"` for `amp-scout` and `amp-checker`, `"high"` for
  reviewer and implementer, `"xhigh"` escalation.
- Agent frontmatter: checker and scout `effort: medium`.

## 6. States and errors

- Reviewer resume fails → fresh checker, ledgered; never silently skipped.
- Pipelined rebase conflict → dropped and redone sequentially, ledgered.
- Worktree setup fails → pipelining off for the run, ledgered.
- A crash mid-pipeline, on resume (ledger line `Task N+1: pipelined (worktree <WT>)` without a
  later `complete`): N+1 counts as merged only when the ledger has `Task N+1: merged (base <BASE>)`
  **and** `amp-wt-<N+1>` is an ancestor of HEAD; then clean up and review `<BASE>..HEAD`. Otherwise
  (including a crash while N+1 was still being implemented, when the temp branch tip is still N's
  head) clean up and redo N+1 sequentially (ledger `Pipeline: off — resume`). Cleanup is always
  `worktree remove --force` and `branch -D`.
- Implementer skipped the full suite but CI fails → existing ship CI fix loop handles it.

## 9. Review Focus

1. A resumed reviewer widening scope in a re-review (blocking on things outside the fix diff).
2. Pipelining: N+1 committed into the main tree or BASE computed wrong, so a review package drops
   or mixes commits.
3. A leftover worktree/temp branch after a drop or crash.
4. Lean rules lost in transit: a rule from amp:lean that no longer reaches implementers or
   reviewers (implementer: ladder, dead code, never-cut, tests, `lean:` markers; reviewer: ladder,
   dead code, never-cut, tags), or a prompt that still points an agent at `amp:lean`.
5. Codex/Claude leakage: claude-only words in `codex/` or vice versa after edits (existing leak test).
