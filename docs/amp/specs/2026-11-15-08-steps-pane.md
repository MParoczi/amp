# Phase 08 — `/amp-steps` and the run row: Spec

## 1. Goal

Phase 08 (`framework/08-steps-pane`) adds a `/amp-steps` pane that turns a project's amp steps on
and off by editing the `## amp configuration` table in `CLAUDE.md`, creating the section, the rows
or the file when they are missing. It also replaces the plugin's status line, which Claude Code
draws as a yellow warning notice, with a row amp draws itself above the prompt. Release 2.1.0.

The request was a plain one; this repo has no roadmap, so the phase id follows the specs before it.

## 3. Architecture

- **`hooks/steps.ts`** (new, pure): reads the seven switches out of a `CLAUDE.md` text and returns
  the text with one switch changed. No engine calls, so it is unit-tested directly, like
  `hooks/run.ts` and `hooks/guard.ts`.
- **`hooks/register.tsx`**: registers `/amp-steps`, draws the pane, and on a pick reads
  `CLAUDE.md`, applies `setStep` and writes it back. The commit button runs git through
  `$.process.run`. The `AbovePrompt` hook draws the run row; the `$.ui.status` call goes.
- **`hooks/run.ts`**: the part of `statusText` after the stage becomes its own function, so the
  row can color the parts.

**Deletions:** the `$.ui.status(...)` call in `show()` (`hooks/register.tsx`). In
`hooks/run-hooks.test.ts` the `ui.status` stub stays only to prove it is never called; every
assertion that read `host.status` (run pickup, plan re-count, oversized or unreadable ledger
skipped, idle outside a repository, a merged run dropping out) is kept and reads the row instead.
Comments that describe the status line (`hooks/register.tsx` header and `show`, `hooks/run.ts`)
are reworded. `statusText` stays: `/amp-run`'s reply uses it.

## 5. Interfaces

### 5.1 `hooks/steps.ts`

```ts
export const STEPS = ['Grill', 'Tests', 'Verify', 'Document reviews', 'Task reviews', 'Final review', 'CI'] as const
export type Step = (typeof STEPS)[number]
export type Switch = 'on' | 'off'
/** One line per step for the pane: what does not run when it is off. */
export const STEP_HELP: Record<Step, string>
/** Each step's value in a CLAUDE.md text; undefined text (no file) is all on. */
export function readSteps(text: string | undefined): Record<Step, Switch>
/** True when the text's table holds all six on/off rows. */
export function hasStepRows(text: string | undefined): boolean
/** The text with `step` set to `value`; unchanged when the step already has it or the change can't be made. */
export function setStep(text: string | undefined, step: Step, value: Switch): string
```

`STEP_HELP`, exact strings:

| Step | Help |
|---|---|
| Grill | `off: no interview and no gate; open decisions become rulings in the PR` |
| Tests | `off: no new tests are written; existing tests stay green` |
| Verify | `off: the local verify run before the PR is skipped` |
| Document reviews | `off: no independent review of spec, plan or roadmap` |
| Task reviews | `off: no per-task review and no fix loop` |
| Final review | `off: no whole-branch review` |
| CI | `off: the PR merges without waiting for checks` |

**Lines.** The text is split into lines with their terminators kept apart: a line's content never
includes its `\n` or `\r\n`, and every existing line keeps its own terminator. Added lines use
`\r\n` when the text contains any `\r\n`, else `\n`. A leading byte-order mark is ignored when
matching the first line and is kept.

**Finding the table.** The section starts at the first line whose content matches
`/^##\s+amp configuration\s*$/i` and ends before the next line starting with `# ` or `## `, or at
the end of the text. The table is the first run of consecutive lines in the section whose content
starts with `|` (after optional spaces). Its first line is the header and its second the
delimiter, by position; the rest are rows. A row's cells are split on `|` not preceded by a
backslash; the key is the first cell and the value the second. Keys compare after trimming
whitespace and backticks, ignoring case. When a key occurs in several rows, the first is the one
read and edited. Headings and `|` lines inside fenced code blocks are not recognized as such: a
`## amp configuration` heading inside a code fence before the real one is a known limit.

**`readSteps`.** A step is `off` when its row's value, trimmed of whitespace and backticks and
lower-cased, is `off`; otherwise `on` (a missing row, table or section, an undefined text, an
invalid value, and for `Verify` any command).

**`setStep`.**

1. *The step already has `value`* (by `readSteps`): the text is returned unchanged, whatever rows
   are missing. An undefined text is returned as the empty string.
2. Otherwise the six on/off rows are ensured, then the change is applied:
   - *No text, or empty text:* the result is exactly this block, each line terminated:

     ```markdown
     ## amp configuration

     | Key | Value |
     |---|---|
     | Grill | on |
     | Tests | on |
     | Document reviews | on |
     | Task reviews | on |
     | Final review | on |
     | CI | on |
     ```

   - *Text without the section:* the block is appended. Before it, line endings are added only as
     needed so that the existing text ends with a terminated line followed by one blank line;
     none is ever removed.
   - *Section without a table:* after the heading line come a blank line, the table (header,
     delimiter, six rows), a blank line, then the original rest of the section. A blank line that
     is already there is not doubled.
   - *Table present:* each missing on/off row is appended at the end of the table as
     `| <Key> | on |`, in the step order. When the table's last line has no terminator (end of
     file), one is added first. Existing rows keep their position and text.
3. *The changed on/off row:* only its value cell changes, to ` on ` or ` off ` (one space each
   side). Its other cells, its key's spelling and its line terminator stay; a row without a
   trailing pipe stays without one, and its value cell then gets the leading space only
   (`| grill | off`).
4. Everything outside the table and the Verify comment line is kept byte for byte.

**`setStep`, `Verify`.** The remembered-command line is
`<!-- amp Verify command: <raw value cell, trimmed> -->`, on the line directly after the table's
last row (never between rows, which would break the table; D6 said "the next line", and below the
table is the nearest place that keeps the table valid). Only a comment in that position counts.
Rule 3's clause for a row without a closing pipe applies to the `Verify` row too.

- *off, the row holds a command:* the value cell becomes ` off ` and the comment line is written,
  replacing one already there. A line that must be followed by an added line (the table's last
  row, or a heading at the end of the file) first gets a terminator when it has none.
  When the command contains `-->` it can't be remembered: the text is returned unchanged.
- *off, no row:* the row `| Verify | off |` is appended at the end of the table; no comment.
- *on* (the row is `off`, by rule 1):
  - *comment present:* the value cell becomes the remembered text (one space each side) and the
    comment line is removed;
  - *no comment:* the `Verify` row is removed.

### 5.2 The `/amp-steps` pane

- `session.start` registers
  `{ name: 'amp-steps', description: 'Turn amp steps on or off for this project (CLAUDE.md)' }`.
- `command.run` for `amp-steps` (arguments ignored) opens the pane (id `amp-steps`, title
  `amp steps`) and returns `{ text: 'amp steps pane opened: turn steps on or off for this project.' }`.
  Outside a git repository it opens nothing and returns `{ text: 'amp steps: not in a git repository.' }`.
- The file is `<root>/CLAUDE.md`, `root` being the repository root the module already holds.
  Every git command of the pane runs as `git -C <root> …`, because `$.process.run` starts in the
  session's directory, which may be a subdirectory.
- **Reading the file** (for a draw and for a pick): `$.fs.exists(path)` decides whether there is a
  file. No file → the text is undefined. A file whose `$.fs.read` rejects (too large, refused) is
  a **read error**: it is never treated as missing.
- The pane, top to bottom:
  1. heading `amp steps` (bold) and a dim line `Written to CLAUDE.md, under "## amp configuration".`
  2. on a read error: `CLAUDE.md can't be read: <message>` and nothing below except the footer.
  3. when the file does not exist: `CLAUDE.md does not exist: the first change creates it.`
     When it exists and `hasStepRows` is false: `The first change adds the amp configuration rows.`
  4. one `Select` per step, in the `STEPS` order, `key` = `step-<Step>` (for example
     `step-Task reviews`), `label` = `<Step>: `, options `on` and `off`, `value` from `readSteps`;
     under each, its `STEP_HELP` line, dim.
  5. when a run is active and its ledger has an `Off:` line (without one, the run reads the
     table live): `A run is in progress: changes apply from the next run.`
  6. when `git -C <root> status --porcelain -- CLAUDE.md` prints anything: a `Button` with
     `key="commit"`, `label="Commit CLAUDE.md"`, and beneath it two dim lines:
     `/amp:phase needs a clean working tree. This commits only CLAUDE.md on the current branch and does not push.`
     and `The repository's commit hooks do not run for this commit.`
  7. a dim footer `Esc closes.`
- The pane is the same on every surface (every surface's element table has `Select` and
  `Button`); there is no text fallback.
- **A pick** (`onSelect(value)`): picks are applied one after another (each waits for the one
  before). Read the file as above; on a read error toast
  `amp steps: CLAUDE.md can't be read: <message>` and write nothing. When
  `readSteps(text)[step] === value`, do nothing: no write, so re-picking a current value never
  creates or touches the file. Otherwise compute `setStep(text, step, value)`. When the result
  differs from `text ?? ''`, write it with `$.fs.write` and redraw
  (`$.ui.invalidate('ui.render')`); when it does not differ, toast
  `amp steps: could not change <Step>; edit CLAUDE.md by hand`. A failed write toasts
  `amp steps: could not write CLAUDE.md: <message>`.
- **The commit button** runs `git -C <root> add -- CLAUDE.md`, then
  `git -C <root> commit -m "chore(amp): update step switches" -- CLAUDE.md` (the pathspec keeps
  anything else that is staged out of the commit). Success toasts
  `amp steps: committed CLAUDE.md` and redraws; a non-zero exit of either command toasts
  `amp steps: commit failed: <first line of stderr, else of stdout>`; a command that can't start
  or times out toasts `amp steps: commit failed: <message>`. It never pushes.

### 5.3 The run row

- `hooks/run.ts`: `export function statusDetail(run: Run, total?: number): string` returns
  everything `statusText` prints after the stage (for example ` · tasks 2, 3 r2 · 1/7 done`, or
  the empty string). `statusText(run, total)` returns
  `` `amp ${run.key} · ${run.stage}${statusDetail(run, total)}` `` and its output is unchanged.
- `show()` no longer calls `$.ui.status`; it still invalidates `ui.render`.
- A `ui.render` hook on `{ component: 'AbovePrompt' }`: with no active run, or while
  `e.props.hasSurvey`, it returns `next(e)`. Otherwise one row, a `Box` holding in order:
  - `amp` — `Text`, bold, `color="claude"`
  - ` <key> · ` — `Text`, `dimColor`
  - `<stage>` — `Text`, bold; `color="suggestion"` for `gate`, `color="warning"` for `stopped`,
    no color for every other stage
  - `<detail>` — `Text`, `dimColor`, omitted when empty
  - when `run.off` holds names: ` · off: <names joined by ", ">` — `Text`, `dimColor`
- `claude`, `suggestion` and `warning` are `ThemeKey` names (the colors a drawn tree may use).
- The row carries no warning mark and no `amp:` prefix; it disappears when the run merges or its
  ledger is deleted, as the status line did. A merged run is never the active run, so `merged`
  needs no color.

### 5.4 Release

`.claude-plugin/plugin.json` `"version": "2.1.0"`; `scripts/test`'s `manifests` case asserts it.

## 6. States and errors

- **No repository:** `/amp-steps` opens nothing and says so; no file is read or written.
- **No `CLAUDE.md`:** the pane shows all steps on and the creation notice; the first change
  creates the file.
- **`CLAUDE.md` exists but can't be read:** the pane shows the error and no selectors; a pick
  writes nothing. The file is never replaced by a fresh section.
- **A row with an invalid value** (for example `Grill | maybe`): shown as on; picking `off`
  rewrites it; picking `on` changes nothing (rule 1).
- **File changed outside the pane between draws:** each pick re-reads the file before editing.
- **Two quick picks:** applied in order, so neither is lost.
- **A `Verify` command that can't be remembered** (contains `-->`): the pick toasts and changes
  nothing.
- **Write fails / commit fails:** a toast with the reason; the pane keeps showing the file's real
  state.
- **Nothing to commit:** the button is not drawn.
- **`CLAUDE.md` untracked:** `git add` makes the commit include it.
- **Session started in a subdirectory:** the pane still edits and commits `<root>/CLAUDE.md`.
- **Commit during an active run:** it lands on the run's branch, like any commit there.
- **Survey in the band:** the run row yields (`next(e)`).
- **VS Code:** the engine raises `AbovePrompt` on terminal, desktop and mobile only, so the row is
  not shown there; `/amp-run` still works.

## 7. Testing strategy

- `hooks/steps.test.ts` (unit, pure): `readSteps` for undefined text, no section, no table, mixed
  rows, backticked and upper-case values, an invalid value, duplicate rows (the first wins),
  `Verify` with a command and with `off`; `hasStepRows`; `setStep` for rule 1 (no change, missing
  rows left alone) and each shape of rule 2, a table on the last line with no final newline, a
  CRLF file including a row with no trailing pipe, a section followed directly by another heading
  or by text, text ending in several blank lines, a leading byte-order mark, key matching that
  ignores case and backticks, and each `Verify` case including the round trip with a command that
  holds backticks and an escaped pipe (command → off → on restores it exactly and removes the
  comment) and the `-->` refusal.
- `hooks/run-hooks.test.ts` (engine harness, the extended `fakeHost`): the pane draws one keyed
  `Select` per step with values from the faked file; a pick writes `setStep`'s result; a missing
  file shows the creation notice, a pick of `off` writes the full block, and a pick of a step's
  current `on` writes nothing; a file that exists but whose
  read rejects shows the error, draws no `Select` and a pick writes nothing; the commit button
  appears only when the faked `git status --porcelain` prints, and pressing it runs the two git
  commands in order with the exact arguments, including `-C <root>` when the session's directory
  is a subdirectory; a failing commit toasts its first stderr line; outside a repository the
  command answers the not-a-repository text. For the row: an active run draws it with the texts
  and colors of §5.3; no run draws none; the `off:` part; `ui.status` is never called; and the
  former `host.status` assertions hold against the row.
- `hooks/run.test.ts`: `statusDetail`; the existing `statusText` expectations stay unchanged.
- `bash scripts/test` and `claude plugin test .` are the gates.

## 8. Docs impact

- `README.md`: in "What the plugin adds to a session", the "Status line" bullet becomes the run
  row (what it shows, the colors, that it sits above the prompt, not shown in VS Code); a new
  `/amp-steps` bullet (what it edits, creation of missing rows/section/file, the Verify
  remember-and-restore, the commit button and that commit hooks don't run for it,
  next-run-only); "Turning steps off" says the rows can be changed with `/amp-steps` or by hand;
  the Contents row for that section mentions `/amp-steps`; "Requirements" and the components table
  in "What runs where" name the run row and `/amp-steps` in place of the status line; the
  "Tested on" version is the one `claude --version` reports when the work is verified.
- `CHANGELOG.md`: `## 2.1.0 — 2026-11-15`.
- `skills/phase/SKILL.md`, "Steps a project can turn off": one sentence that `/amp-steps` edits
  these rows.
- No file under `hooks/` may contain the text `AGENTS.md` (a `scripts/test` case greps for it).

## 9. Review Focus

1. `setStep` never damages the rest of `CLAUDE.md`: bytes outside the table and the Verify comment
   are unchanged, including CRLF files, a table at the end of a file with no newline, and a table
   followed directly by text.
2. A `CLAUDE.md` that exists is never replaced by a fresh section because a read failed.
3. The Verify round trip: a command with backticks or an escaped pipe survives off → on exactly.
4. The commit button commits only `<root>/CLAUDE.md`, from any session directory, even when other
   files are staged, and never pushes.
5. The run row never shows a stale run and yields to a survey; nothing calls `$.ui.status`.

## 10. Out of scope

Other configuration keys; `AGENTS.md`; a skill form of the command; changing an active run's
`Off:` line; amp:phase adding rows by itself; pushing; making `claude plugin validate --strict .`
pass.
